## 日常健康檢查

在正式 Python 3.12 環境執行：

```bash
python -m scripts.project_health --profile core
python -m pytest -q
python -m scripts.verify_models
python -m scripts.verify_package
```

在只安裝 `dashboard/requirements.txt` 的網頁環境執行：

```bash
python -m scripts.project_health --profile dashboard
```

健康檢查只讀保存資料，不下載行情、不抓新聞、不訓練、不寫訊號、不更新 manifest、不執行 Git 保存。會檢查套件存在與支援範圍、程式語法、凍結 bundle、訊號及帳本完整性、保存研究與原始輸入雜湊，以及 V2／V3 歷史報告。`core` 另檢查交易日與來源橫斷面；`dashboard` 無需 TensorFlow／Torch／sklearn。

JSON 的 `status` 為 `pass`、`waiting` 或 `fail`；只有 `fail` 回傳 1。來源未追上目前已完成交易日，或合法部分進度尚待恢復，標為 `waiting` 且回傳 0，讓後續更新仍可執行。此命令的等待狀態與每日執行器的等待回傳 2 是不同介面。套件檢查不取代乾淨環境重新安裝與 `pip check`。

正式與網頁 Actions 都會先執行對應健康檢查。網頁 CI 的觸發路徑也包含相關程式、測試、研究報告與設定，避免只改底層程式時漏掉網頁驗證。

正式來源更新的時間上限可用 `TW_LSTM_MARKET_TIMEOUT_SECONDS` 或 `python -m scripts.update_market_data --timeout-seconds 1800` 設定，接受 1～3,600 秒。這個上限涵蓋來源更新工作，不代表整個每日訓練只需 30 分鐘；直接呼叫原 `build_snapshot()` API 仍保留同步行為。程序群組終止的實測環境是 Linux，與 GitHub Actions 相同。

## 保留的限制與操作規則

- 排程仍為週一至週五 17:37／21:37，另每日 09:17 重試；GitHub 排程與第三方服務仍可能延遲或停機。測試不能保證未來永不失敗，來源沒有準備好時應保持等待與保存證據。
- 不把「沒有取得新聞」補成中性新聞，不把延遲執行改成事前發布，不以修改雜湊或模型卡消除完整性錯誤。
- 真正完整性錯誤會讓 Actions 失敗並阻止發布，以免錯誤資料被當成成功結果。先查看健康檢查 JSON、失敗步驟與保存 artifacts；預期來源等待可由下次排程恢復。
- 保持 444／555 共用預測核心與原本訓練入口，555 V2 凍結推論、V2.11 不可覆寫訊號、五日交易排程與日誌／新聞展示均保留。V3 維持獨立探索研究，未因本輪健康檢查自動改選或每日重訓。
- 完整性與可重現性通過，不等於歷史新聞時點證據已補足，也不代表 V2／V3 已勝過 0050。原研究結果與限制仍適用。
