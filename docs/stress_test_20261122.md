# 2026-11-22 故障注入與並行壓測

本輪使用隔離目錄、真實子程序與本機 Git bare remote，保留既有推論程式、權重、訊號及研究封存。目標是驗證失敗後能否安全恢復；一般單元測試之外，另實際終止程序、同時競爭鎖、改動提交期間的檔案，並重跑修補前的程式證明問題存在。

## 重現與修補

| 實際故障 | 修補與驗證 |
| --- | --- |
| PID 鎖剛建立但還沒寫入時，可被另一程序當成舊鎖刪除，導致兩個寫入者 | 改用持續存在的 OS 鎖。24 個同時競爭程序各自完成一次，沒有重疊持鎖；空白、負值、巨大數字及錯誤 PID 不影響真正擁有權。 |
| 主程序結束後，孫程序仍可能晚寫 canonical 檔案 | Linux 使用獨立程序群組；逾時、中斷與父程序正常結束後清除殘留程序。舊版已實際觀測到延遲標記檔出現，修補後不再出現。 |
| 主控遭 SIGKILL 後無法執行清理，舊模型仍可能寫檔 | Linux 監督程序使用核心父程序死亡通知，終止其擁有的程序群組；監督程序持有同一鎖，避免死亡通知尚未處理就被新執行搶入。實測暫停監督程序、殺死主控後仍無法取鎖，恢復監督程序後子孫程序結束且可重新取鎖。 |
| successful status 搭配空檔、截斷或 NaN CSV，後續重跑仍永遠命中壞快取 | 只讀核對五檔、日期、模型、預測期限、有限數值、原生預測／NAV／指標與協議。壞快取改為未命中；三套真實 11/20 輸出仍正常重用。 |
| 555 的 444 核心已重算，仍可能重用舊配置 | 555 必須符合目前 444 預測來源雜湊。 |
| 報告接受只有代號／日期卻沒有有效預測的 CSV | 新報告拒絕缺預測及 NaN／Infinity，有限負值和零預測照常接受。測試假資料補成有實際數值的協議，原封存不改寫。 |
| 提交前驗證通過，但 Git hook 在提交途中改動狀態或加入其他檔案 | 提交後逐檔核對先前已驗證的 bytes 與 commit blob；以提交前 HEAD 檢查已發布內容。拒絕未選取內容，撤回本次 checkpoint、保留磁碟檔案與 hook 的其他 staging。 |
| 未發布的 checkpoint 已改寫舊訊號／嘗試紀錄，HEAD 自身不能作舊證據 | push 前對照遠端追蹤基準，阻止改寫已發布紀錄。 |
| rebase hook 在重排後另加入程式碼或留下 staging | 最後 push 前重新驗證待發布提交、遠端基準與工作目錄／index，拒絕推送並保留額外工作。 |
| hook 另建立 commit，回滾可能刪掉額外工作 | 先核對唯一父提交；HEAD 已超出本次 checkpoint 時保留額外 commit 並拒絕自動發布。 |

鎖檔現在會保留在 `logs/orchestrator/run.lock`，內容中的 PID 僅供診斷；OS 鎖才是擁有權。程序被終止後 OS 自動釋放鎖，不依賴刪除 PID 檔恢復。正式 Linux／GitHub Actions 使用同一條程序群組處理路徑；Windows 分支保留相應實作，這輪真實多程序壓測在 Linux 執行。
